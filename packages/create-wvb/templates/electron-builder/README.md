# {{projectName}}

An Electron app whose UI is served from a Webview Bundle (`.wvb`) over a custom `app://` protocol,
packaged into installers with **electron-builder**.

The web UI lives in its own workspace (`web/`) and is packed into a single `.wvb` archive at build
time. In production the main process serves that archive directly; in development the *same URL* is
proxied to the Vite dev server, so you keep hot reload without changing a line of renderer code.

## Quick start

```sh
{{pm}} install
{{pmRun}} dev
```

That starts the Vite dev server and opens Electron pointed at it.

To run against a real packed bundle instead — the same path a shipped app takes:

```sh
{{pmRun}} start
```

To build distributable installers:

```sh
{{pmRun}} dist
```

## How it works

The window always loads one URL:

```
app://{{bundleName}}.wvb/
```

The bundle name is the host with the **`.wvb` suffix stripped**, so `app://{{bundleName}}.wvb/index.html`
resolves to file `/index.html` inside the `{{bundleName}}` bundle. That name comes from the `name`
field of `web/package.json` (npm scope stripped), and the bundle version comes from its `version`.

`src/main.ts` configures the resolver as `{ segment: 'stripSuffix' }` rather than leaving the default
(`first`), because a project name can contain a dot (`acme.web`): with `first`, `acme.web.wvb` would
resolve to bundle `acme` — which `wvb builtin` never packed — and `start` would 404. `stripSuffix`
keeps the name whole.

What sits behind that URL is what changes:

| Command | Handler | Serves from |
| --- | --- | --- |
| `{{pmRun}} dev` | `proxyProtocol('app')` | the Vite dev server (hot reload) |
| `{{pmRun}} start` | `bundleProtocol('app')` | `bundles/{{bundleName}}/{{bundleName}}_<version>.wvb` |
| packaged app | `bundleProtocol('app')` | `<resources>/bundles/…` |

Only one handler can own a scheme, so `src/main.ts` builds the `protocols` array conditionally
rather than registering both. Keeping the URL identical across dev and production matters: the web
origin never changes, so anything origin-scoped (storage, cookies, CSP, service workers) behaves the
same in both.

`app.isPackaged` alone can't tell `dev` from `start` — both run unpackaged — so `dev` passes a
`--dev` flag. `app.isPackaged` still gates it, which means a packaged build can never be pointed at
a dev server, even if someone passes `--dev`.

The `dev` script hardcodes port 5173 in two places — the `wait-on` gate and the `app://` proxy target
— so keep Vite on 5173 (see Limitations). `WVB_DEV_SERVER_URL` overrides only the proxy target the
Electron process reads; it does **not** move the `wait-on` gate, so on its own it can't retarget `dev`.
It's the way to point `dev:app` at an already-running server on a non-default URL.

## Packaging

`{{pmRun}} dist` runs **electron-builder**, configured in `electron-builder.ts`. Two things there are
load-bearing for a Webview Bundle app:

- **Builtin bundles.** The config is wrapped in `withWebviewBundle(...)` from `@wvb/electron-builder`,
  which composes an `afterPack` hook. At package time it reads `wvb.config.ts`, packs `web/` into a
  `.wvb`, and copies it into the packaged app's `Resources/bundles` — exactly where `@wvb/electron`
  looks at runtime. This runs **only when you package** (`dist`); `{{pmRun}} dev` and `{{pmRun}} start`
  never go through electron-builder, so in development you stage bundles yourself with
  `{{pmRun}} bundles`.
- **The native addon.** `@wvb/node` ships its `.node` binary in per-platform packages
  (`@wvb/node-darwin-arm64`, …). A native binary can't be loaded from inside the asar, so
  `asarUnpack: ['**/node_modules/@wvb/node*/**']` keeps the whole family unpacked. Don't remove it.

The config file must keep the name `electron-builder.ts`: electron-builder only auto-discovers
`electron-builder.{yml,yaml,json,json5,toml,js,cjs,ts}`. A `build` field in `package.json` would also
take precedence over this file — don't add one.

## Project layout

```
{{projectName}}/
  src/main.ts          main process: registers the protocol, opens the window
  src/preload.ts       exposes window.wvbElectron to the renderer
  web/                 the web UI — its own workspace; packed into the .wvb
  wvb.config.ts        how bundles are packed and installed
  electron-builder.ts  electron-builder config; installs bundles in afterPack
  tsdown.config.ts     builds main + preload into dist/
  bundles/             generated by `wvb builtin` (gitignored)
```

## Two things that are load-bearing

**1. `wvb()` runs at module top level.** It calls `protocol.registerSchemesAsPrivileged()`, which
Electron only honors *before* the `ready` event. Move it inside `app.whenReady()` and the scheme
loses its privileges — `fetch`, service workers and CORS break in confusing ways. For the same
reason, always `await instance.whenProtocolRegistered()` before `loadURL`, or the first navigation
can race the handler and fail.

**2. The preload is bundled, on purpose.** Electron sandboxes renderers by default, and a sandboxed
preload can only `require('electron')` — nothing else. A preload that calls
`require('@wvb/electron/preload')` at runtime therefore fails with `module not found`, and it fails
*silently*: the page still loads, but `window.wvbElectron` is `undefined` and every bridge call
breaks. `tsdown.config.ts` inlines `@wvb/electron/preload` into a self-contained `dist/preload.cjs`
(~1 kB, `electron` its only import), which a sandboxed preload can run. Keep it that way; the
alternative is `sandbox: false`, which trades away the sandbox for no real benefit.

## Where bundles live

`wvb builtin` packs `web/dist` and installs it as `bundles/<name>/<name>_<version>.wvb` alongside a
`manifest.json`. The `outDir: './bundles'` in `wvb.config.ts` is not arbitrary — unpackaged,
`@wvb/electron` reads builtin bundles from `process.cwd()/bundles`, so this is what lets
`{{pmRun}} start` find them with no `source` config at all. Packaged, it reads `<resources>/bundles`
instead — which is exactly where `electron-builder.ts`'s `afterPack` hook copies them. Both are
defaults, which is why `src/main.ts` never mentions paths.

Downloaded (over-the-air) bundles live under `userData/bundles` and take priority over builtin ones.

## Talking to the main process

The preload exposes `window.wvbElectron`, the transport `@wvb/bridge` expects. Add `@wvb/bridge` to
the `web/` workspace and the renderer can inspect what's installed:

```ts
import { source } from '@wvb/bridge';

const current = await source.loadVersion('{{bundleName}}');
```

`remote.*` and `updater.*` calls fail with `remote_not_initialized` / `updater_not_initialized`
until you add an `updater` block to `wvb()` in `src/main.ts` pointing at a remote endpoint. See the
over-the-air guide for integrity and signature verification.

## Limitations

- **The main process is not hot-reloaded.** `web/` reloads on save; after editing `src/main.ts` or
  `src/preload.ts`, restart `{{pmRun}} dev`.
- **The dev orchestration assumes port 5173.** The `dev` script waits on `tcp:127.0.0.1:5173` and the
  proxy targets `http://localhost:5173`. If Vite falls back to another port (5173 already taken), the
  `wait-on` gate never clears, times out after 30s, and `concurrently -s first` tears the run down.
  Setting `WVB_DEV_SERVER_URL` does **not** fix this — it moves the proxy target but not the `wait-on`
  gate. Keep 5173 free, add `server: { strictPort: true }` to `web/vite.config.ts` so a clash fails
  loudly instead of drifting, or edit the port in both the `dev` script and `src/main.ts` together.
- **Package managers.** Any of `npm`/`pnpm`/`yarn`/`bun` work. The workspace layout needs a couple of
  manager-specific files, which this template ships: `pnpm-workspace.yaml` (pnpm ignores the
  `workspaces` field and would otherwise skip the `web/` deps) and `.yarnrc.yml` pinning
  `nodeLinker: node-modules` (the internal `npm --prefix web` scripts need a real `node_modules`, which
  Yarn's default PnP linker doesn't create). Both are inert under the other managers.
- **`bundles/` is generated.** It's gitignored; rebuild it with `{{pmRun}} bundles`.
